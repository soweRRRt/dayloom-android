# Архитектура Dayloom

## Принципы

Dayloom строится local-first: UI не зависит от сети, а прикладные данные остаются в приватном каталоге приложения. Сеть изолирована в `core:updates`. Между Compose UI и источниками данных используются immutable state, события и `Flow`; тяжёлая работа выполняется вне main thread.

## Границы модулей

| Модуль | Ответственность |
| --- | --- |
| `app` | Application, Hilt composition root, startup, адаптивная корневая навигация и update dialog |
| `core:model` | Общие сериализуемые модели, UUID-идентификаторы, настройки |
| `core:designsystem` | Цветовые схемы, типографика, shapes, spacing, motion и общие компоненты |
| `core:ui` | Переиспользуемые loading/error/empty preview-состояния |
| `core:storage` | DataStore для малых настроек; JSON envelope, миграции, атомарная запись и вложения |
| `core:security` | Контракты блокировки и реальный AES-GCM cipher с ключом Android Keystore |
| `core:notifications` | Контракты будущего единого планировщика уведомлений |
| `core:updates` | Изолированный GitHub Releases provider, transport и SemVer |
| `feature:*` | UI и экранное состояние конкретного продуктового раздела |
| `benchmark` | Macrobenchmark для cold start и переключения основных вкладок |

Feature-модули не обращаются друг к другу. Переходы между ними связывает `app`, поэтому будущая замена реализации раздела не меняет соседние разделы.

## Файловое хранение

Каждая предметная область получит отдельный файл. Корневая структура — сериализуемый envelope с `schemaVersion` и payload. `FileJsonStore` сериализует изменения под `Mutex`, пишет temp-файл, принудительно сбрасывает его на диск, сохраняет предыдущую версию как backup и выполняет atomic move, когда файловая система это поддерживает.

Чтение валидирует схему и payload. При повреждении основной копии предпринимается восстановление из backup; если это невозможно, вызывающий код получает типизированную ошибку. Миграции являются явной цепочкой между версиями. Абсолютные пути не попадают в модель вложения: используется стабильный `AttachmentId`.

## Безопасность

Обычные модульные JSON-файлы никогда не используются для паролей. Vault шифрует сериализованный payload через AES-256-GCM с уникальным IV и AAD; неэкспортируемый ключ Android Keystore требует недавней системной аутентификации. В памяти расшифрованные записи существуют только в активной сессии, которая автоматически блокируется через минуту и при выходе с экрана.

## Обновления

`UpdateSource` отделяет UI от канала распространения. Текущий GitHub provider делает короткий HTTPS-запрос к API, игнорирует drafts/prereleases стабильного канала, безопасно валидирует release URL и сравнивает SemVer. При переходе в Google Play provider можно заменить, не переписывая экран настроек и диалог.

## Следующие этапы

Следующие расширения — локальные изображения для подходящих сущностей, настраиваемая блокировка всего приложения и единый движок уведомлений с выбором WorkManager/AlarmManager по точности сценария. Перед публичным релизом Vault потребуется отдельный threat-model review на физических устройствах разных производителей.
